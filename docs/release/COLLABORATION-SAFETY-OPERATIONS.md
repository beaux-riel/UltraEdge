## App and backend contract

`ue_live(action,args)` retains existing actions. Migration `supabase/collaboration/002_safety.sql` copies the original implementation to a client-inaccessible `ue_live_core` and adds a checked wrapper. No client table grants or permissive RLS policies are added. Existing optimistic timing revisions, request deduplication and owner permissions remain in the core.

- `abuse_report`: `{roomId,userId,reason,details,requestId}` returns `{id}`. Both guests must currently belong to the room; self-reporting is rejected. Reasons are `harassment`, `hate`, `sexual_content`, `threats`, `other`; details are optional, max 1,000 characters. Request IDs deduplicate retries; ten new reports per reporting guest per rolling 24 hours. Failed submissions are not queued offline and UI never announces success without a receipt.
- The private `ue_live_abuse_reports` table stores reporter/subject guest IDs, room reference, reason/details, timestamps/status, and a bounded evidence snapshot: event name, subject display name, subject timing observations and, only for reports about the owner, the shared plan. No invitation code or session token is copied. Clients cannot inspect reports, review them or change their status. The app includes neither moderator tooling nor notifications. Only an authorized backend operator can access the queue.
- Evidence format version 1 preserves room/subject IDs and plan revision even if the live room is later removed. For owner reports the full plan is retained only if its serialized JSON is at most 262,144 bytes; otherwise `plan` is null and `planExcerpt` contains the first 16,000 characters of serialized plan text (an excerpt, **not valid complete JSON**). Observations are a deterministic latest-first sample (received time descending, checkpoint ID/kind tie-break), capped at 100 rows and 131,072 serialized bytes. `truncation` records original plan bytes, limits, total/included observation counts and separate plan/observation truncation flags. JSON escaping/UTF-8 overhead is bounded too; a large valid room cannot make reporting fail the 600,000-byte evidence constraint. Reason/details are never shortened by this sampling. Ordinary validation, membership and report quotas still apply.
- Reviewers must inspect truncation metadata: a sample can omit the offending content. Use the preserved room/subject IDs to inspect current authorized server content where it still exists, and seek clarification through the verified private support process if needed. An excerpt is not proof that omitted content was safe, nor a complete historical record. No additional data collection or retention guarantee is implied.
- `block_user`: `{roomId,userId}` returns `{removedRoomIds}`. Blocker leaves every common room they do not own. Where blocker owns the room, target is removed and invite rotates. Client purges departed-room cache and pending observations after server acknowledgement; retained rooms hide target observations. Server reads hide historical observations between blocked guests; server joins reject either guest entering a room containing the other. Blocks are across rooms, not merely a UI mute.
- Block actions, joins, reporting and deletion use a shared transaction advisory lock to prevent interleaved join/block membership checks and reporting quota races. This intentionally serializes a bounded private-team workload; load-test before larger use. Existing room locks and owner checks remain. Do not bypass the public wrapper with new privileged endpoints.
- Blocks last until either identity is deleted. There is no unblock UI in this iteration. Guest identities are not verified people: another identity can evade a block. Existing cached/exported copies on other devices cannot be recalled; offline devices cannot immediately receive access changes. Owner removals without blocking retain the original historical-report semantics.

## Filtering is limited

Server triggers reject new/updated display names and all string values in shared snapshots matching configured whole phrases after Unicode NFKC/case/punctuation normalization. `ue_live_content_terms` has just four starter entries: two English profanities and two explicit threat/self-harm harassment phrases. These are **limited baseline filtering, not full hate, sexual-content, threat, multilingual or semantic moderation**. Spelling obfuscation and other abusive language can evade it; innocent context can be rejected. In-app reporting and blocking are additional controls, not proof of comprehensive moderation.

No retroactive scan occurs when a term changes. Before release, operators must review existing names/plans against the current rules, handle matches, curate broader proportionate terms (normalized lowercase plain words/phrases), and validate false-positive cases. Provide a private way to contest an incorrect filter. Do not edit the original migration to adjust a deployed term list; use an independently reviewed follow-up change.

## Deletion and retention

“Delete my collaboration data” is visible at the bottom of the live team panel, including inside an open room and when no room/actor is cached. Events → Join / open a live team race opens the panel; Settings → Privacy & Support explains the route. No guest is created solely to delete it.

- A rejected/unacknowledged server deletion preserves rooms and pending observations so the user can retry. Deletion is idempotent for a still-valid guest token even after its user row is gone, allowing retry after a lost response. Expired/lost credentials remain a recovery limitation requiring the operator's verified private support process.
- Once the server acknowledges deletion, local collaboration cache is cleared even if local sign-out throws or returns an error. UI distinguishes completed server deletion from local session/cache cleanup problems. Local race plans are untouched.
- Deleting either guest cascades associated blocks and abuse reports/evidence. This intentionally prioritizes the current guest deletion contract; it is **not** a policy of retaining all abuse evidence for investigations. Closing a room instead nulls the queue's room reference and retains evidence for review.
- There is no automatic queue aging/purge job. Before launch, the operator must choose and publish an evidence-retention limit, implement a reviewed purge schedule, determine appropriate deletion/legal handling, and validate it. Do not promise a duration yet. Provider auth logs, external logs, backups and previously downloaded copies are separate; this SQL does not erase those.

## Migration / release procedure — requires approval

1. Confirm the actual deployed `ue_live` body and schema match `001_live_rooms.sql`. Compare any production changes before replacing the RPC; the core is a copy, not an automatic merge. Take the operator's approved backup and review grants/definer ownership. Use a privileged database owner; no service key belongs in app configuration.
2. On an isolated staging database, apply `001_live_rooms.sql` only if not already installed, then apply `002_safety.sql` once. The latter is a one-time transactional migration, not rerunnable. **Never rerun 001 over 002**: it would replace the safety wrapper. Do not run either against production without explicit approval.
3. Run `bash scripts/test-live-safety-local.sh` for a disposable local PostgreSQL cluster, plus dedicated Jest tests. It binds only a temporary Unix socket, not a TCP listener; stops the cluster on exit and prints retained logs. It never uses project Supabase credentials. This validates real PostgreSQL behavior with minimal auth functions, not real Supabase JWT/network/device behavior.
4. Verify staging permissions explicitly: `anon` cannot execute `ue_live`; `authenticated` can execute only the wrapper, cannot execute core/filter functions and cannot access safety tables directly; RLS remains enabled. Test deployed roles/default grants as well as those mocked locally.
5. Two test devices: create/join, offensive name/plan rejection, submit report then block, target-owner / blocker-owner / third-party-owned common rooms, rotated invitations, blocked rejoin both directions, historical observations hidden, stale/offline state, observation conflicts, revoke/leave/close, and guest deletion including failure/retry. Use disposable identities with approval, never real team identities. Test the exact final binary.
6. Deploy only in an approved maintenance/release window. Old apps can continue timing operations but lack reporting/block UI; server filtering/block enforcement still applies. Do not ship the new UI against a backend without migration: it will reject the new actions. Preserve the safety wrapper during rollback; prefer a reviewed forward fix instead of reopening unsafe direct access.
